Your owl, driven by your timings

Frames, captions and millisecond values copied from the frames.json you attached, run by the rules in your README: 80 ms tick, redraw only when the string changes, elapsed time reset on a state change, trailing spaces kept. The pass shown is one full cycle — idle through the 8300 ms blink (half closed 4900–5020 ms, closed 5020–5270 ms, half closed to 5390 ms), thinking for 12 s (4 × 1400 ms segments, question mark in the third), then done — then it repeats. This is what the Rust module in the fork implements; the captures under it are that module in the real terminal.

  • Welcome step — idle owl over the brand line (dropped if the terminal is too short, and dropped when the connect step brings its own owl).
  • Connect step — idle owl at the top of the panel, until the server is saved.
  • In a session — thinking while a turn runs, done for 4 s after it stops, gone on esc or an error. The block costs five rows above the composer while a turn is running.
  • With animations = false the same states show their static frame, no cycling.

Getting owl onto your machine

In the pushed repo: cd Owl/owl && ./install.sh. The folder now carries a prebuilt release binary (prebuilt/, built from this source on the build cluster; x86_64 Linux with glibc 2.39 or newer). When it runs on your machine, install.sh copies it to ~/.local/bin/owl in a second — no compiling, no Rust toolchain. If it cannot run on your machine, install.sh says so and builds from source like before; ./install.sh --force-build always compiles. The self-test covers both paths, including an install with no cargo on PATH at all.

Tested here: the whole flow above ran end to end against the local mock, including saving to config.toml and the second run skipping the connect step. Not tested here: your Open WebUI on your LAN, which this sandbox cannot reach, so it has only been proven against this machine's endpoint and mock. The owl module is a re-implementation of the frames and timings you attached — the JavaScript in your package itself was never attached, so behaviour is matched to your spec, not to your code. Two decisions are still yours:

  1. Should the owl also sit idle above the composer while the session is waiting, or only during and just after a turn (what it does now)?
  2. Connect screen on first run only when nothing is configured (the current rule), or on every startup?
